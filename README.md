## 设置日志

1. 修改保留天数，允许 1 到 30 天。
2. 修改容量上限，允许 8 到 4096 MiB。
3. 点击“保存设置”，核对保存结果与概览中的已保存选项。设备执行仍以实际读回为准。

默认每 3 秒记录四台机器，滚动保留最近 7 天，容量上限为 4096 MiB。容量包含清理所需的预留工作空间。容量先到上限会清理最旧记录，实际历史可能少于设置天数。缩小设置会立即删除超出范围的本服务历史，不能通过 UI 恢复。日志不含设备 token。

传感器轮询和原始记录目前均以 3 秒为目标间隔；0.5 秒采集要求尚未实现，本次 Journal 修复不改变采样周期。`board_temp` 显示为“非GPU硬件最高”，是现有可信 CPU / ACPI / NVMe / 网卡 / WiFi 等输入的跨器件最大值，含保护代理，不是独立主板温度；字段、传感器身份、分组、温度数值及保护阈值不变。

每个原始段配有至多 1024 字节的 `.jsonl.bounds.json` 派生缓存，保存全部有效有限数字时间戳的精确最小/最大值及原始文件 dev/inode/size/mtime_ns 身份。原始 JSONL 仍是唯一数据依据。缓存缺失、损坏或身份失配不能证明范围；单次 `bounds(path)` 最多重建一个 320 KiB 段，兼容本机观测到的最大 277392 字节历史段。该上限统一用于新段、读取、修复及调用方临时工作空间预留；单条记录仍至多 64 KiB。每次 prune 的重建读取合计最多 320 KiB，全部原始读取与重写合计最多 8 MiB，并有 32768 目录项、8 MiB 元数据及协作式 2 秒预算；超限抛出 OSError，沿用现有存储故障保护，不全库扫描。总容量与保留期不变，清理前验证所有段及自有字节清单，按正常时间戳/容量策略保留或清理原始数据。范围维护不要求时间戳单调。

`Journal.index_ready(root)` 是不实例化 Journal 的只读检查，最多检查 32768 目录项、8 MiB 元数据及协作式 10 秒，不读取原始正文、不清理工作文件。成功返回 ready、segments、raw_bytes、index_bytes，否则抛出 OSError。旧日志须由停止状态下的有界离线准备逐段调用 bounds，部署流程复用同一 readiness 检查；本修复不新增 rebuild_index API 或后台写入者。缓存、孤立缓存及识别出的工作文件均计入容量；仅在对应原始段正常删除时移除其普通 sidecar，符号链接和无关文件保留。历史查询可只读验证缓存以跳过范围外的闭合段，不修改共享范围或修复缓存，元数据读取也计入原有查询预算。

追加和替换先同步原始文件，再原子发布已 fsync 的缓存并同步目录；任一步失败保留实际原始结果，撤销内存证书并报告失败，不授予学习信用。不完整末行拒绝继续追加，保留已有数据。Linux 路径实际调用目录 fsync；Windows 的此 Python API 不提供等价目录同步，Windows 聚焦测试只验证逻辑，不能证明 Linux 崩溃持久化。身份验证依赖独占写入及没有同身份的外部篡改；预算检查不能中断阻塞的系统调用。

温度历史的曲线继续显示时间桶内最高温。下方表格显示同一次日志快照的控制方式、有效请求、实际档位、RPM、设备读回时间、四台节点各自的 CPU / GPU / 非GPU硬件最高及采样时间和保护原因。表格按日志写入顺序倒序，最多 200 条，不保证墙钟时间排序；超出时明确显示截断。选择本地结束时间并点击“查询”可查看更早的保留时段。结束时间留空时每 30 秒跟随实时刷新。图表与表格使用同一时段，但时间桶峰值不是同一时刻的原始快照。

新记录的 `ts` 为采样开始时间，`snapshot_at` 为控制状态快照时间，`control.manual_level` 为当时的已保存模式。设备时效按快照时间与 `fan.verified_at` 比较，超过 9 秒标记过期，未来读回标记时间异常。旧记录未保存的模式和快照时效显示未知，不回填；缺失和离线节点保持可见。概览也显示设备读回时间。实际档位只来自设备读回，不能用请求档位替代。

`GET /api/history?hours=1&until=UnixSeconds` 返回 `rows`、`samples`、`samples_truncated`、`from`、`to` 和聚合说明。`until` 可省略，必须是有限、非负且不晚于当前时间的秒数；`hours` 必须大于 0 且不超过 720。起点按当前保留时间裁剪，完全过期的时段返回空结果。`Journal.history` 在同一扫描中生成曲线与最多 200 个经过字段筛选的原始快照。

历史使用独立的单线程读取器，不占用日志写入线程，也不更新 Journal 的共享范围缓存或清理文件。每次查询最多读取 64 MiB、检查 32768 个目录项和记录行，并在检查点限制为 2 秒；单段读取最多 256 KiB 加一个溢出检测字节。损坏行也计入预算。超过预算返回 503 并提示缩小范围，不返回部分结果。已缓存且不再增长的段可按时间范围跳过；未缓存的段也计入预算。读取期间仍可能发生保留清理。取消请求仍占有读取锁，直到真实线程结束，重叠请求返回 429。时间预算在目录项、段和记录行之间检查，不能中断操作系统正在执行的磁盘读取。

保存期间所有设置字段禁用，同一时间只接受一次保存，重叠请求返回 409。设置原子提交并同步目录后才按新设置清理历史。清理失败会报告设置已保存但维护失败，历史可能已部分清理。提交或同步异常后，服务重新验证磁盘设置并在可确认时更新内存，同时保留独立 `settings_error` 全风保护，直到下一次可靠保存。日志成功不会清除此错误。超时表示结果未知，界面刷新服务器状态；新草稿保留，不能把草稿当成已保存或已执行。

## 连接外部风力设备

唯一连接流程是米家扫码、查看设备列表、主动选择、确认绑定。

1. 在“连接散热设备”勾选社区协议同意项，点击“米家扫码连接”。
2. 用中国大陆账号的米家 App 扫码，在手机确认登录。
3. 等待枚举完成，在米家设备列表查看名称、型号、IP、DID、在线状态和不可绑定原因。下拉框默认不选择设备。IP 使用云端返回值，可能是缓存地址；缺失或无效时显示“IP 未知”，不主动发现地址。
4. 选择可绑定的固定净化器，再勾选保存与控制确认，点击“确认绑定并启用温控”。改变选择会清除确认，状态刷新保留仍有效的选择。
5. 核对概览中的实际档位、电源、模式和正 RPM。绑定成功只表示固定身份验证通过并保存了本地凭据。

目前只允许已验证本地 0–16 档范围的物理单元 `192.168.3.24 / zhimi.airpurifier.m2 / DID 70632677 / MAC 78:11:dc:47:87:bf`。列表不按净化器型号过滤，显示本次返回的所有有效设备，包括音箱、传感器及未知型号设备。其他设备仅显示元数据，选项禁用且不能绑定，即使型号相同也不适用此设备的标定。选择本身不触发控制，服务不会自动选择或自动绑定。

扫码授权后，服务先请求账号级 `/app/home/device_list`，再合并家庭设备列表，以包含单独共享的设备。账号请求使用 `getVirtualModel=true`、`getHuamiDevices=1`、`get_split_device=false`、`support_smart_home=true`，沿用当前 serviceToken 加密传输。协议参考 [hass-xiaomi-miot](https://github.com/al-one/hass-xiaomi-miot/blob/master/custom_components/xiaomi_miot/core/xiaomi_cloud.py) 和 [micloud](https://github.com/Squachen/micloud/blob/master/micloud/micloud.py)，未复制或引入其 SDK。

枚举完成返回 `ready`，即使本次列表没有目标。固定身份匹配但 token 缺失、null 或空字符串时，设备仍显示，标为 `credential_unavailable` 且不能绑定。相同元数据重复记录合并，缺少凭据不会覆盖另一条有效凭据；不同有效 token、身份矛盾、元数据冲突及其他无效 token 均拒绝本次枚举。列表缺失不等于账号没有该设备，真实账号是否返回共享设备及可用凭据仍需实际扫码验证。

服务只保留固定目标的一个私有 token。其他设备密钥处理后立即丢弃，公开列表只允许 `did/name/model/ip/online/selectable/reason` 字段。列表最多受 30 个家庭、每家庭少于 200 条、账号与家庭合计 1024 条原始设备记录限制，重复记录也计数。缺少设备列表、列表类型错误、`has_more` 或 `hasmore` 表示未完、超界及冲突记录均拒绝，不返回部分成功结果。名字清除控制字符并限制为 64 字符，空名字显示“未命名设备”。型号缺失、null 或空字符串显示“型号未知”；其他非字符串、超过 128 字符或含控制字符的型号仍触发验证错误。固定 DID 缺失、null 或空型号仍触发身份不匹配。未知在线状态显示未知，不作为本地身份验证的替代。成功枚举仅记录家庭数、原始记录数、显示数、目标凭据是否可用、目标是否可见及账号记录数，日志参数均为数字，不记录设备标识或凭据。

绑定请求仅接受 `POST /api/xiaomi/qr/bind` 的 `owner`、`consent`、`did`，DID 必须是字符串 `70632677`。排队、已开始或已完成的重复请求也先检查同一固定 DID。首次绑定需要当前会话有效的候选及凭据，取得配对锁时再次验证。入场后清除会话候选和 token，重试仍能取得同一绑定结果，不重复验证或保存。排队期间可取消或过期，已入场事务通过屏蔽请求取消完成验证、保存与安装。失败保留原执行设备；绑定不重置 MotorSchedule、尝试次数或降档计时。

扫码使用现有社区提取器协议，不是官方 OAuth。临时会话最多 180 秒，云端给出的更短期限会进一步缩短。取消、过期、退出和重启清除未绑定的临时凭据。入场后的绑定会完成其持久化事务。绑定 token 原子保存到持久状态目录的 `device-token`，Linux 权限为 `0600`。正常重启从此文件读取并重新验证固定物理身份，无需再次扫码；已有电机执行预算继续按原逻辑恢复。账号会话和本地 token 都不保证永久有效，失效需重新扫码。页面不接收密码或手填 token，不在浏览器存储保存会话。

账号凭据和设备密钥不进入公开 JSON、温度记录或服务日志。仅复用已观察到的中国大陆扫码传输，保留 TLS 验证、主机和路径白名单及禁止重定向规则。来源与许可见 `THIRD_PARTY_NOTICES.md`。

已移除 HA 缓存、手填 token、LAN 扫描和证书下载入口及其工作池。旧连接路由返回 404。HTTPS 服务继续使用原有 `tls.crt` 和 `tls.key`，不改证书文件。保持本服务为该净化器唯一控风方。

## 使用预防性温控

默认手动 16 档。取得设备有效读回并验证现场风路后，在“温控方式”选择自动或手动 0 到 16 档。修改字段仅产生草稿，点击“取消草稿”恢复服务器已保存设置，不发送 API 请求。点击“保存设置”才提交。概览分别显示已保存选项、保护后的有效请求和设备实际读回；正且有限的 RPM、近期读回、电源 on、favorite 模式以及实际档位匹配才可确认执行。0 档仍在运转，不是关机。

自动模式可在 0 到 16 档之间调节，服务显式使用最低 0 档。核心 Controller 默认最低 10 档。手动 0–16 档是最低需求，不是上限，保留全部温度、负载、传感器、采样和故障保护。启动为 16 档，必须获得真实风机读回和完整安全基线。每次试降都要等待执行确认、观察回温并重新满足稳定条件，不能仅按每三十秒持续降档。实温紧急线、连续预测到达硬线、热节流、失联、关键传感器缺失或反馈过期仍请求全风。每次保存重新建立 16 档保护及稳定期，保留温度历史和物理执行预算，不保证立即达到所选档位。各场景条件见下文。

仅 Wi-Fi 温度缺失允许有界告警观察。最后一次真实读数必须通过全机保护检查，原始升温率低于 0.3°C/s，或者符合完整冷态资格。缺失年龄不得超过 30 秒，且 `最后温度 + 原始非负升温率 × (缺失年龄 + 30秒)` 不得超过板级目标减 2°C。冷态资格要求至少 30 秒完整历史、实温不超过目标减 5°C、稳健预测余量充足且没有近期快速升温事件。持续快速升温读数不授予缺失宽限。启动证据不足、已触发保护或连续性丢失不会因传感器消失而解除。缺失不刷新读数、时间戳或资格，也不能确认试降、完成观察、继续降档或纳入学习。超过 30 秒、预测余量不足或其他可信传感器缺失仍请求全风。上述时间和余量是工程容错边界，不是厂家热额定值。

`POST /api/settings` 仅接受 `{"retention_days":7,"max_log_mb":4096,"manual_level":16}` 的三个字段。`manual_level` 为 `null` 时自动，为整数 0 到 16 时手动，不接受布尔值、浮点数或旧 API 字段。磁盘上的旧 `full_speed:true` 仅在加载时映射为 16，`false` 映射为 `null`，启动不重写旧文件；下一次成功保存只写规范字段。

唯一的 `MotorSchedule` 属于固定物理设备，替换 token、周期身份复核或退出清理不会重置预算。`state/motor-budget.json` 仅保存版本、固定身份、尝试次数、预期档位和故障。每次生产启动恢复预算，并重新施加完整八秒修正窗口和三十秒降档窗口，不使用磁盘时间戳、墙钟、启动 ID 或 pending 标志。两次预算耗尽即使文件中的故障布尔值为 false，也按故障恢复。

仅当预算文件和 `device-token` 的目录项都确认不存在时，首次启动才能创建零预算。悬空链接不算缺失，权限错误不算缺失。已有 token 但缺预算、损坏、身份不符或不安全的预算会显示只读故障，同时继续温度监控。不要删除预算文件来绕过故障。只有认证设备的有效全风、favorite、正 RPM 读回，且预算重置可靠保存，才能恢复这种不确定状态。

`fan_apply(device, wanted, schedule)` 与退出清理使用同一执行约束。每轮修正在任何可能修改设备的调用前原子保存尝试次数和预期档位，并同步预算所在目录。恢复时先保存原有保守债务，保留尝试次数、预期档位（未知则使用最大档）与故障，两次尝试按故障处理；原子保存及目录同步均成功后才将内存预算清零。首次确认无预算、无 token 且无旧债务的零预算初始化不变。恢复成功后磁盘债务可能暂时落后于已清零的内存，重启会恢复该保守债务并重新要求有效物理读回恢复；耗尽或不确定状态需要新的有效全风读回。下一轮成功持久预约以新次数 1 替换旧债务，结束上一物理修正周期。持久化失败保持可见只读故障，不显示虚假的执行确认。进程中断可能耗掉一次尚未执行的预约，但不会凭重启补回已消耗次数。

最终写边界仅允许整数 0–16，实际读回不截断。开机、切模式以及任何阻塞保存后重新读取最新请求。单轮只合并到更高目标，更新预期档位可靠保存后再次读取请求，防止保存期间出现全风请求却写入旧的降档目标。实际降档步长与三十秒资格在档位写入前再次检查。已匹配状态不写；单纯档位差异不重复开机或切模式；读回未知保持只读。

“目标已匹配”与“实际设备健康”分别判断。近期有效、在本地范围内、电源 on、模式 favorite 且 RPM 为正的无故障实际读回，即使仍在逐步降档，也保持当前较低请求，不因待执行提示立即反弹至 16。故障、范围异常、未知读回、缺少身份配置或过期反馈仍请求最大档。任何写入尝试先失效旧读回的确认时间，丢失应答不能使用写入前读回放松保护。

每次尝试在设备调用前可靠计入预算，每个可能修改设备的调用结束时更新时间，包括异常或丢失应答。最后一个修改调用完成后八秒内只观察、合并最新请求并显示待执行。未解决的一次修正最多两次尝试，耗尽后故障锁定。改变请求、等待、重启或替换凭据本身不能清故障。有效匹配读回与可靠预算重置才能恢复。最大档请求和退出清理没有绕过执行约束的路径。

实际降档一次最多比当前真实读回少一步，降档调用完成后至少三十秒才能再次降档。此执行约束独立于控制器的保护恢复和低档试降计时。八秒只约束两轮修正，不是每个开机、模式、档位命令之间的额定间隔，也不是厂家额定稳定时间。电机实际爬升由固件管理，软件时间戳不能证明在途延迟命令或物理响应。实际风量、电流、稳定时间和连续运行仍须现场标定。本服务不写 RPM、电压、PWM 或固件设置。

若全风读回后温度仍超过保护线，检查设备位置、进出风口和室温，并减少热负载。本服务不自动关机或降频。温度不能仅靠软件保证低于某个值。

查看温度时注意数据名称。CPU 显示 ACPI 最热区保护代理，不是已校准的独立 CPU 结温。非GPU硬件最高包含 CPU、ACPI 代理、NVMe、网卡、WiFi 等现有可信输入，跨器件取最大值，不是独立主板探头；ACPI 通道的具体 CPU 子部件映射尚未确定。SPBM 温度与 ACPI、NVIDIA 读数有差异，单列显示且不作为唯一保护源。

本服务控制外部净化器，不覆盖 DGX 内置风扇固件。CPU 和 GPU 的 60°C 控制目标、70°C 持续升温紧急点及 75°C 工程硬线，板级的 65°C 目标和 75°C 硬线是工程策略，不是硬件额定极限。官方 [DGX Spark 硬件说明](https://docs.nvidia.com/dgx/dgx-spark/hardware.html) 的环境温度要求不能当成芯片阈值。传感器接口参见 [Linux thermal sysfs 文档](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)。

## 有界观察学习与自动发布

版本14使用一个控制器拥有的模式状态及一个当前执行记录。服务继续每3秒调用 `decide`，仍是唯一物理执行者。界面显示请求档位、实际档位、RPM、模式、当前原因和等待进度。寄存器匹配及正RPM只证明旋转，不证明风量或散热容量。0档仍保持开机和正RPM。

CPU/GPU达到60°C时需求至少10档，不把已有更高档位直接降到10。准备区在全部CPU/GPU降到58°C时退出。只有同一传感器的实温或当前可信预测严格超过CPU/GPU60°C、板级65°C，且没有持续有效降温响应，才可累计升档不足证据。实际确认至少10档后，每30秒有效证据请求相邻加一档。见证、档位、身份、来源、工作负载或调用模式改变都重新计时。降温响应要求同一传感器完整30秒覆盖、稳健斜率不大于-0.01°C/s，以及最近至少6秒连续不增且有严格下降。单帧负导数不算响应。

CPU/GPU达到70°C且当前可信连续升温时请求16。独立75°C工程硬线保留2°C实际缓冲，CPU/GPU及板级达到73°C即保护，包括平稳或降温读数。同源当前连续升温的30秒预测达到75°C也保护。孤立尖峰及旧快速标志不单独触发全风。节流、温度缺失、采样停滞、无效电机反馈、执行超时及服务或存储故障继续请求16。75°C是工程选择，不是寿命或厂商安全保证，内置风扇固件不变。

启动或真实故障后须取得新鲜完整温度及匹配推进的16档反馈，再取得30秒安全基线。温度历史须先覆盖30秒。冷态进入要求全部CPU代理及GPU不超过45°C，支持的板级传感器不超过55°C，已知稳定功率低于80W，每个CPU及GPU负载低于10%，完整推进遥测和健康匹配反馈。进入后CPU/GPU采用47°C退出迟滞，板级仍须不超过55°C。每30秒相邻有效证据请求下降一档，可到手动下限或0。重复、待执行或缺失帧不计时并断开区间，后续不能补算。新负载或持续加速停止冷态下降。合法已有功率阈值仍可保留10档。实际冷态原因带有 `[cold-release]`。

确认降档后的不超过2°C、仍低于目标的安全小回温，保持实际档位观察。参考温度固定，首次回温后的90秒绝对截止不重置，60秒有效观察后可重新评估收敛。到期缺少证据时保持并重新资格，不制造下降或成功。47.1°C退出冷态本身不恢复到10档，须取得普通资格或出现独立需求。真正收窄目标余量才允许相邻修正或回退，保护仍优先。

热保护原因解除后，原危险传感器保持可信降温、全部CPU/GPU不超过66°C、其他可信温度有安全余量时，可分别累计30秒请求15、14等相邻恢复。60°C以上保留至少10，平坦的目标以上缺口不能冒充恢复。58°C以下安静基线可普通恢复，约40°C低负载可走冷态。旧升温标志不重启当前危险。

非冷态普通搜索保留90秒完整收敛窗口、60秒准入、至少120秒原档实际停留、目的档确认后120秒观察及固定300秒观察截止。普通试验保留固定传感器和工作负载参考，按当前余量及双向变化评估，只有可归因的普通试验可以产生自动 `success`。缺样或不收敛耗尽观察记录无结论，回退并取得新资格。失败边没有永久封禁。冷态释放、回温、分级、待执行、恢复、故障、手动及不确定片段一律不授予学习信用，冷态保持0也不能继承释放时钟。

一个未完成执行事件固定保留原起点、目的、请求时间及请求后60秒截止。模式、上下文、手动变化或重复保护可更换当前目的及其请求时间，但不得续期原事件。当前目的须匹配推进的请求后反馈，放弃目的的迟到读回不能确认。先判截止再判确认，到期读回不能免除执行故障。电机继续执行8秒修正间隔、30秒物理下降和两个持久化尝试，未更改服务轮询或物理债务。这些间隔是项目暂定限制，不是厂商认证的电机极限。

决定和历史API保留 `trial` 作为下降试验记录，保留其失败、失效、无结论或完成结果及原观察截止。新增 `execution_trial` 为当前执行的派生诊断，不增加可变控制器副本。`from` 是本执行事件起点，`to` 是当前目的，`original_from` 和 `original_to` 保留最初请求。`requested_at`、`original_deadline` 和 `destination_requested_at` 均为有限单调时间，分别表示原请求、原60秒截止和当前目的请求。升档匹配后状态为 `confirmed`，不会继续显示 `pending`。界面及历史优先显示当前执行，同时保留下降试验结果。旧历史缺少该字段时不补造执行或时间。验证器应读取 `execution_trial` 并以推进的 `fan.observed_mono > destination_requested_at` 验证当前目的，不能用旧 `trial` 代替当前执行。

执行超时记录保留原请求和原截止，后续失联、存储保护或重复保护不能擦除。仍请求16并禁止下降和学习，直到新鲜16档反馈及完整启动基线取得资格。未知功率不阻止截止前的物理匹配确认，但禁止温度资格、下降和学习。普通待执行下降一旦失去当前目标余量，恢复先前确认档位并失效未确认试验，保留原执行截止。合法Wi-Fi短暂缺失保留已知传感器身份，缺失帧不赚取证据也不能跨缺失补算时间。

遥测分别校验单调采集间隔、节点请求年龄及来源墙钟年龄。来源年龄按 `sampled_at + (now - requested_mono) - source_ts` 计算，允许-2至6秒，避免将来源墙钟直接与单调时间比较。2秒未来容差仅容纳小幅采集及节点时钟偏差，6秒过去上限与现有请求新鲜度一致。推进但旧900秒的温度仍是故障。反馈新鲜度继续为9秒，正RPM及执行匹配仍须独立成立。

已知功率达到80W、授权来源的40至80W合法学习阈值或持续负载至少30%保守保留10档。未知功率冻结下降及学习，不单独构成热紧急。手动增加可直接抬高最低档位，手动下降仍须相邻确认和当前安全证据，手动记录永不自动学习。

学习器仍只归约已同步原始日志，发布空闲整机功率阈值，不发布散热容量。`Learning.baseline` 保留55°C的保守空闲拟合标准，与运行60°C目标不同。120秒学习稳定性、15分钟桶、6小时评估、72小时窗口、训练及后时段验证、40至80W阈值和每次5W限步均保留。仅.180/.181精确 `spbm` 整机来源可发布。原始峰值及排除计数仍记录冷态等不合格行。

普通搜索可容纳短时后台波动，但不提供严格学习资格。`learning_eligible` 独立要求当前实际档位、节点身份、来源、功率和负载在完整推进的120秒窗口内严格稳定。每个CPU/GPU负载须低于10%，窗口负载范围不超过5个百分点，功率范围不超过10W或均值的10%。重复反馈、缺样、超过6秒间隔、待执行、冷态释放或恢复不授予信用。窗口滚动淘汰旧变化，重新取得当前严格证据后允许资格恢复，旧上下文不会永久阻断。

检查点维持schema1，控制器版本14。严格接受整数版本2至10、12、13、14，拒绝11及未知或畸形版本。已知旧版本先完整校验结构、计数、策略形状及可用证据，再无错误清空旧学习状态，绝不重新标记为14。合法14恢复描述性证据并清空运行连续性。原始7天日志、存储预算、设置、绑定、TLS及电机预算不迁移。依据 AGENTS.md，发布失败保留当前代码、学习状态和故障证据，修复后向前发布，不自动恢复旧程序、旧检查点或启动旧服务。预检查失败不改动运行服务，安装不完整不启动混合版本。危险降档后恢复先前安全风力属于设备保护，继续保留；没有真实转速读回不能声称已确认全风。历史 R3 发布入口和已结束试验不复用，新实机验收须遵守该次授权的负载、时长及安全边界，不因失败自行延长或重启。软件时间线及历史重放不证明带载散热能力，安静验收不能验证60/70°C带载行为。

## 检查常驻服务

在 3.180 上执行以下命令。

```sh
systemctl is-active dgx-thermal
systemctl is-enabled dgx-thermal
systemctl show dgx-thermal --property=MainPID,NRestarts
journalctl -u dgx-thermal -n 20 --no-pager
```

正常状态为 `active` 和 `enabled`。systemd 在服务退出后重启，并检查采集、风机工作线程心跳。没有重启整台 DGX 做验收。3.180 断电时，软件无法记录或调控另外三台，外部风机停电也无法由软件补偿。

## 更新服务代码

当前应用、工具、测试和回放样本的完整清单由 `release_index.json` 提供，不再维护容易遗漏的手写部署文件列表。该清单是离线候选定义，不是原生安装准入。更新时保留 TLS 文件、设置、历史、已存凭据和电机预算。先在隔离目录运行统一检查，再使用新的、独立复核过的发布流程。不能并行启动两个控制进程。

在有现成依赖的隔离环境运行：

```sh
python -B -m unittest discover -v
```

隔离测试目录需要全部 `test_*.py`，以及 `.audit/lower-airflow-live-trace.json` 和 `.audit/background-probe-long-trace.json` 两个不可变回放样本。`discover` 包含场景、低风力及窗口策略回归，不能只运行基础测试代替完整验收。回放样本不参与生产控制。

测试使用假 Cloud 和临时状态目录，不登录真实账号，不访问真实设备。Node 用于离线界面交互检查。完整 Linux 文件权限、无跟随打开与目录同步验收需要在 ARM/Linux 上运行，Windows 的替代检查不能证明这些持久化语义。
